# 2026-11-17 底部导航动画重组优化

本轮保留的改动只涉及主页底部导航。使用 Standard Debug 包，在 PKG110 / Android 15 真机测试。没有修改 R8、构建优化策略、页面过渡、媒体数据加载和返回位置逻辑。

## 最终实现

将 `MainBottomNavigation` 从 `MainActivityScreen.kt` 提取到独立文件，并将每个标签拆成独立的组合函数。指示器缩放在 `graphicsLayer` 中读取，透明度在绘制节点中读取，图标和文字颜色使用延迟读取的颜色函数。动画推进无需重新执行整行导航的组合。

保留原有导航项、选中状态、无障碍 Tab 语义、重复点击选中项的处理、尺寸、字体、圆角，以及 350 ms 指示器动画和 150 ms 颜色动画。文字使用与原 Material3 `Text` 相同的显式 `labelMedium` 样式；已通过原实现的像素对照。

曾尝试将专辑封面的 `BoxWithConstraints` 替换为测量后的尺寸回调。该方案需要额外的测量后状态更新，未取得足够的收益证据，最终已撤回。封面生产代码和原有封面测试均与本轮开始时一致。

## 已确认的收益与回归

测试专用 `CompositionTracer` 记录真实 Compose 编译器事件；生产代码不安装跟踪器。

| 真实主页操作 | 原包整行导航组合次数 | 最终包整行导航组合次数 |
| --- | ---: | ---: |
| 媒体库、分类、统计、设置、目录，首次各切换一次 | 每次 23 | 每次 1 |
| 相同顺序再切换一次 | 每次 23 | 每次 1 |

最终包的每次切换只重新执行两个选中状态发生变化的标签。单独的动画回归还在手动推进时钟时断言：选择更新完成后，动画帧不再执行导航行或标签的组合函数。

播放器和编辑器两种模式均与冻结的原导航实现进行像素对照，包含初始帧、动画中间帧和结束帧。每帧差异阈值为总像素的 0.3%，颜色通道差异超过 0.02 才计为不同；两种模式均通过。没有通过删除动画来降低组合次数。

最终安装包上共 38 项设备验证通过：37 项回归和 1 项真实主页诊断。范围包括动画像素对照、导航回调和选中项重复点击、主页重组隔离、快速反向过渡、真实音频封面、专辑布局与排序、分类滚动条、多级目录和五类分类返回位置。

## 整体性能结果与限制

测试期间发现设备后台游戏和自动化进程持续运行，CPU、温度和内存负载变化明显。早期低负载原包与后期高负载候选包不适合直接比较，未用来计算优化幅度。随后又执行两组原包 → 最终包交替安装测试；全程使用 `adb install -r`，保留应用数据，并确认亮屏。

每轮按“媒体库 → 分类 → 数据统计 → 设置 → 目录”循环五次，25 次点击，每次输入命令后等待 80 ms，连续三轮。下表为不开跟踪时的 gfxinfo 累计卡顿比例和直方图 P95，均来自本轮最终的底栏单项改动。

| --- | ---: | ---: | ---: | ---: |
| 第一组 / 1 | 86.36% | 67.27% | 800 ms | 700 ms |
| 第一组 / 2 | 75.90% | 52.50% | 150 ms | 150 ms |

两组数据方向有所改善，但外部负载没有受到控制，且实际渲染帧数也会变化；不能把这些比例之差当成稳定收益。第一次交替测试中，每次点击等待 350 ms 的六次往返数据如下，同样只作为观测记录。

每包每组另做三次进程冷启动，`am start -W` 的 `TotalTime` 中位数分别为：第一组原包 936 ms、最终包 934 ms；第二组原包 1007 ms、最终包 1052 ms。没有稳定的启动改善，本轮不宣称解决启动卡顿。早期一次设备息屏期间的启动采样已排除。

最后一组相同切页脚本的 Perfetto 记录：

| 主线程切片 | 原包总耗时 / 最长 | 最终包总耗时 / 最长 |
| --- | ---: | ---: |
| `Compose:recompose` | 825.94 / 20.26 ms | 731.45 / 28.34 ms |
| `AndroidOwner:measureAndLayout` | 1321.27 / 122.48 ms | 1233.19 / 74.43 ms |
| `Choreographer#doFrame` | 5590.89 / 180.18 ms | 4248.25 / 116.82 ms |

这些轨迹也存在负载差异：两个后台进程的 CPU 时间合计分别约 25.64 和 30.66 CPU 秒，轨迹长度均为 18 秒，不能单独据此宣称整体耗时下降。轨迹解析分别报告 19 和 52 个负时间戳丢弃事件。

剩余长帧仍包含应用自身的布局工作。最终包最长布局切片为 74.43 ms，其中主线程实际运行约 72.56 ms、处于可运行等待约 0.76 ms；它需要继续减少布局和首次构建的工作量，不能全部归因于后台竞争。底栏优化消除了一个确定的重复工作来源，尚未解决全部切页和启动长帧。
