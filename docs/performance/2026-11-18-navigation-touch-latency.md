# 2026-11-18 主页点击后停顿、延迟切页的专项定位

用户明确卡顿体感集中在点击主页底部标签后，画面先停一下，再开始切换。本轮改为测量输入到首帧的响应，不用整段动画的平均掉帧率代替该指标。

## 测量方法

设备当前 1.2.6 / code 16 debug 包，APK SHA-256 为 `327a035cee36ed88684b2020be84d3d9a129b52d4b0066dbc9ab83bbbedb218f`。主包与本次测试编译使用的工作区主包哈希一致；未安装新主包或改变 ART 编译策略。

新增仅存在于 androidTest 的 `MainNavigationTouchLatencyTest`：使用真实 MotionEvent 注入和真实系统帧时钟，不使用 Compose 测试时钟，也不安装 CompositionTracer。在 Window.Callback 接收 ACTION_UP 时开始计时，记录点击派发结束；新目标成为选中页后，通过 OnDraw 与 registerFrameCommitCallback 观察首批帧的提交。

指标是“应用收到抬手事件 → 新选择状态下首个绘制帧的提交”，包含组合、测量、绘制与提交等待。它不是转场完成时间，不保证此帧已经在屏幕呈现，也不保证初始透明度大于零；仍可确认应用无法在该时间前提交本次选择对应的新画面。事件注入到 Java 派发的队列等待另记录在最终诊断格式中。

依次点击媒体库、分类、数据统计、设置、目录，每页在前三次帧提交后再等待 650 ms，连续三轮。保留真实数据、显示模式和目录，没有为测试清空库或重设偏好。

点击处理只有约 2–7 ms，明显更长的等待发生在处理之后、首个相关绘制帧提交之前。重复进入分类、统计和目录时仍有约 200–300 ms，不能只归因于进程冷启动。

## Perfetto 对齐

另执行一组带 Perfetto 的相同测试，以 `NavigationTouch`、`NavigationDrawStart`、`NavigationFrameCommit` 标记对齐主线程工作。跟踪本身有开销，不与无跟踪值相减计算收益。

示例：

- 首次进入统计：点击派发约 3.91 ms，首帧提交约 413.67 ms；其中一个 `measureAndLayout` 约 303.20 ms，相关慢帧约 389.38 ms。
- 再次进入分类：点击派发约 2.93 ms，首帧提交约 256.89 ms；其中一个 `measureAndLayout` 约 162.82 ms。
- 再次回目录：点击派发约 7.59 ms，首帧提交约 295.31 ms；其中一个 `measureAndLayout` 约 168.96 ms。

确认当前延迟的重要来源是导航后的组合、布局和子组合挤在首批转场帧中。目标页面必须完成这些工作后才能提交画面，因此用户会看到旧页面停留，然后才出现切换。若主线程错过数个动画帧，实际可见过渡也会被压缩，形成停顿后跳过去的体感。

当前 `MainTopLevelPageTransition` 在过渡完成后移除旧页面组合，保存的是页面数据/滚动状态，并未保留所有页面的 UI 组合；返回页面仍需要重建可见内容。快速点击时，旧页退场与新页构建还可能重叠。新目标的第一次构建和重复重建应作为下一步优化重点。

这些数字覆盖真实内容，不能仅凭顶层切片认定统计页中的单个控件是唯一热点，也不能保证把数据库刷新延后一帧就能解决全部问题。本轮不改生产导航或动画，先建立准确的响应指标。后续改动应同时验证首次点击、重复点击、目标页首个可见内容和动画帧间隔，避免用更快的标签反馈掩盖目标页仍未出现。
